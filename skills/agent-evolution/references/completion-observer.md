# 終了時の失敗から開始する

監視は通常作業のツール結果を観測し、作業終了時の判定を確認する。非ゼロ終了コードだけでスキルの失敗とは決めない。監視フック自身はモデル・候補生成・評価を起動しない。

## 承認の対象

- 起動確認は終了結果が `failed` の場合だけ。`passed`・`unverified`・`cancelled` では提案しない。
- 通知に失敗の要約と関連スキル候補を付けて1回だけ尋ねる。スキル未特定ならその旨を表示する。
- 人が明示的に承認した後に通知IDへの `decide --decision approve` を記録する。辞退なら `decline` を記録して終了する。無回答や通知の発生は承認ではない。
- Codex・Claude Code・Grok CLIでは会話内で質問する。Stopフックが継続を要求し、失敗の要約を付けて1回だけ尋ねる。Piは確認ダイアログ、OpenCodeは通知に記載された明示的な返信文を使う。
- Grok CLIのStopは、標準出力へ `{"decision":"block","reason":"..."}` を返すと理由がモデルへ渡り、同じターンで継続する。`StopCancelled` は中断として扱い、起動は提案しない。対話セッションでは、ホーム以外の作業フォルダで `/hooks-trust` が必要になることがある。

## 承認後

1. 指定された通知と現在の作業結果を確認し、スキルの問題、製品コードの問題、環境障害を区別する。失敗のすべてをスキル変更で解決しようとしない。
2. 対象スキル、再現条件、期待結果、評価可能な成果物を整理する。会話全体・認証ファイル・秘密を評価課題へコピーしない。
3. 実モデルを呼ぶ前に、使用する製品・モデル・推論量・評価回数・候補生成回数を明示する。既存の有効な許可を引き継ぎ、使い切った以前の予算を復活させない。
4. 評価には共有スキルのコピーを使う。改善候補の採用は別途、比較結果と差分を人が確認してから行う。

終了結果はフックが提示する配布版の絶対パスと隔離オプションを含む `outcome` コマンドで記録する。配布版が使用できない場合に、Documents内の開発コピーや `.venv` へ自動で切り替えない。監視用コメント・JSON・記録コマンドの出力を通常の回答本文へ付けない。記録できない場合も本文への埋め込みで代用せず未記録として扱う。スキル未読や終了判定未記録を、失敗確定として扱わない。

新規作業の監視記録はセッション開始時の作業フォルダ内の `.evolution-observer/` に保存する。フックが提示する `--state`・`--cwd`・`--session` を結果記録と承認/辞退で引き継ぐ。ツールの作業フォルダが変わっても保存先を差し替えない。既存の明示 `--state` は旧保存先でも有効。権限不足等で記録できなければ表示された原因を確認し、自動の権限昇格や別保存先への切替は行わない。

共有スキルの利用手順は呼び出す製品・版を固定しない。自動の終了監視と実評価には、それぞれ製品別の接続コードが必要。版の更新時は必要条件を再検査し、同じ評価runに更新前後の結果を混ぜない。

Grok CLIは `~/.claude/settings.json` のフックも読み込む。`GROK_SESSION_ID` または `GROK_HOOK_EVENT` がある実行では、`--agent grok` 以外の入口は記録せず終了する。Claude Code 側の登録は残す。

設定・解除・保存先・検証範囲は、配布リポジトリの `OBSERVER.md` に記載する。
